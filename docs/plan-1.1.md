# 1.1 计划 —— Full Transcript / 全见

## 观测质量的天花板不在解析

`NativeActivityHarvest` 每次扫描都从零重读一个有界窗口（`readWindow`）：

```swift
let windowCap = id == .codex ? 8_000_000 : (id == .pi ? 496_000 : 1_000_000)
let headLimit = id == .pi ? 96_000 : 64_000
```

绝大多数 Agent 是**头 64 KB + 尾约 936 KB**。并且：

```swift
let records = (ext == "jsonl" || ext == "ndjson") && !window.truncated ? … : 0
```

**一旦截断，记录数就是未知。** 0.98 让它诚实地报未知，但那是症状，不是病。

`Application Support/Pulse` 下有 attention.tsv、账本、设置、launch-state、rollback ——
**没有任何采集器的持久状态**。每一次扫描都是失忆的。

### 后果：观测质量与会话重要性成反比

一场跑了几小时的会话轻松超过 1 MB，于是中间那一大段**永远读不到** —— 不是这一拍读不到，
是永远。里面的工具调用、错误、token、改过的文件，全部不可观测。

**你最在意的那种会话（长的、复杂的、跑了半天的），恰恰是 Pulse 看得最差的那种。**

托盘上的事实一直停在「标题 + 路径 + 最近一个工具 + tokens」，不是因为解析不出来，
**是因为那些字节从来没被读过**。

## 这一版换的：从「重读窗口」到「增量摘要」

每个会话文件记住 `(路径, 文件标识, 头部指纹, 读到的偏移)`，每次扫描只折入新增的字节，
摘要存盘。中间那段不再被跳过 —— **它只是在流过的时候被读了一次**。

**这一版不阻塞于 P0-0。** 解析缺口确实要等真机证据，但天花板不是解析设的，是「只看两头」
设的；修它只需要改 Pulse 怎么读它本来就在读的文件。

### 明确不做（本版）

| 项 | 理由 |
| --- | --- |
| 让摘要**取代**窗口读取 | 窗口喂着全部现有事实。这一版只**增加**新事实，一行现有行为都不改；替换是下一版的事，且要先有一版的实测垫底 |
| 凭猜扩展解析 | 只认几个明确的键，其余跳过。P0-3（解析缺口）仍等真机证据 |
| 统计大盘 | 新事实必须回答「这个会话现在怎么样」，不是「本月概览」 |
| 存正文 | 工具**名**是厂商 token；它要跑的命令是你的事，不落盘 |

### 用户看得见的变化

**超过 1 MB 的会话，记录数从「未知」变成精确值。** 这是这一版唯一的、也是真实的显示变化。

摘要里已经有工具直方图、最近工具序列、错误与 token 总量，以及「同一个工具连着调了 N 次」
的打转信号 —— 它们**这一版还没上托盘**，只进了安全支持报告（`sessionDigests:`）。

### 已知缺口（写下来，不假装没有）

1. **窗口读取仍然存在。** 摘要目前是**额外**读一遍增量，不是替代。稳态多花的是增量那几 KB，
   而不是整个窗口 —— 但「省掉窗口重读」这句话本版**不能说**，因为没做。
2. **新事实还没上界面。** 打转信号是这一版最有价值的东西，我把它留在了模型与支持报告里：
   托盘每加一个事实都要过 EXPERIENCE 的「一行最多 4 个事实」这一关，值得单独一版认真放，
   而不是塞进来。
3. **token 语义有分叉。** 摘要累计的是**整场会话**的用量，而托盘现有的 tokens 是**最近一条
   消息**的用量。两者都对，但不是一回事，**所以本版没有让摘要覆盖它** —— 先想清楚显示哪一个，
   再动。

## 为什么这个顺序

先把「读完」这件事做对并钉死不变量（分片 == 一次性），再谈用它做什么。理由和 0.98 一样：
**一个孤立的数字不可归因**，而一份会缓慢算错的摘要比一个诚实的窗口糟得多。所以这一版
宁可只兑现一个显示变化，也要先让底下那层可证。
