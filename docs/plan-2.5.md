# 2.5 计划 —— Confirmed / 兑现

## 一件事：判决的下场，从「Pulse 说它做了什么」变成「观测到了什么」

2.4 交付了这个产品最重的一个动作，而 Pulse **至今不知道那个动作有没有生效**。

`writeRespondVerdict` 成功后界面说「判决已写出，等你的同步工具送达」。这是一句关于
**Pulse 自己**的陈述。三种截然不同的结局在用户眼里一模一样：

| | 实际发生了什么 | 界面说什么 |
| --- | --- | --- |
| ① | hook 取走判决 → 厂商采纳 → agent 继续 | 判决已写出 |
| ② | hook 根本没取到（hold 超时 / 同步太慢）→ 厂商提示照常弹 | 判决已写出 |
| ③ | hook 取走了 → **厂商没认这个形状** → 厂商提示照常弹 | 判决已写出 |

这个产品最深的一条规矩是**没测到的不许说**（2.2 为 CPU 立，2.3 推广到全局）。
**判决的下场是目前唯一一个逃过这条规矩的重要事实。**

---

## 第一层（本版做）：认领动作在磁盘上留了痕

`claimVerdict` 的认领方式就是把 `verdicts/<id>.json` 原子改名成 `<id>.json.used` ——
**认领本身是一个文件事实，不需要任何推断**：

| 盘上的样子 | 含义 |
| --- | --- |
| `<id>.json` 在，未过期 | 已写出，还没被取走 |
| `<id>.json.used` 在 | **已被 agent 取走** |
| `<id>.json` 在，已过期 | 过期了也没被取走 —— 厂商提示已经自己弹了 |

于是那句话从一态变三态。对 2.4 的本机场景尤其值钱：往返是毫秒级，行上几乎立刻能
确认，**这正是让人敢按那个按钮所需要的回执**。

**远端不这么报。** 远端判决写进 `verdicts.d/<host>/`，`.used` 改名发生在**另一台
机器**上，它回不回来取决于用户的同步工具是不是双向的 —— Pulse 无从得知。远端继续说
今天那句话，它本来就是诚实的。**能观测的才报，这正是本版要立的规矩，不能自己先破。**

## 第二层（本版不做，挂着）：厂商到底认没认

区分 ① 和 ③ 要看厂商是否采纳。P0-0 的 Q2 证据显示厂商内部会产出
`decisionReason:{type:"hook",hookName:"PermissionRequest"}` —— 但那是**从二进制里读到
的内部代码路径，没有证据说明它会落进 Pulse 读得到的笔录**。当前采集器一个相关字段都
没解析。

**先取证，再动手。** 假设它在笔录里就是在犯本版要修的那个错。取证需要一台装了
Claude Code 的真机答一次，然后看那一场会话的 JSONL 有没有留下痕迹 —— 那同时会把
`plan-2.0` 的 P0-0 第 2 步还掉。本版把这一层明确挂起，不假装。

## 顺带必须做的两件

### S2 · StatusStore 拆分

已经 **5019 行**（1.2 时 4548，每一版都在长）。本版还要往里加判决生命周期状态，那是
第 13 种职责。`plan-2.4` 的先决门槛里就写了这条，上一版没做，这次不能再欠。

做法是**零行为变更的搬运**：把内聚的 `extension StatusStore { … }` 块整组移进新文件。
Swift 的 extension 不改变类型，所以**一个调用点都不用动**。搬运时连同它们的 `private`
辅助一起搬（`private` 是文件作用域），不为了搬家把可见性放宽。

### 2.4 新面的清扫

2.3 那份审计**早于** `PromptVisibility`、本机 respond 路径、第二个通知 category。
先做审计再动手，已发现两条：

| ID | 项 | 为什么要命 |
| --- | --- | --- |
| E-1 | 横幅的「拒绝」由**上一拍**的匹配决定 | `applyScan` 先发通知，`refreshRespondInbound` 后跑。一个刚到的权限请求**在它唯一那条横幅上永远没有拒绝按钮** —— 2.4 的招牌功能在最该起作用的时刻是缺席的 |
| E-2 | 请求只往**可见行**上匹配 | 匹配对象是 `snapshot.rows`，那是 `SnapshotBuilder.window` 裁过的可见列表。行被挤出窗口的 agent，其权限请求拿不到任何 Respond 控件 |

## 逐项清单

### P0 · 缺陷

| ID | 项 | 验收 |
| --- | --- | --- |
| E-1 | 匹配移到发通知之前 | 请求随扫描一起进 `applyScan`，在快照建好之后、`postWaitingNotifications` 之前完成匹配；新请求的第一条横幅就带拒绝 |
| E-2 | 匹配全量行 | 对 `cachedAll` 匹配，不对窗口匹配 |
| E-3 | 扁平树也要清理 | `cleanupOutbound` 目前只在 hook 写请求时跑；App 侧扫描也带上，否则关掉功能后残留不会消失 |

### P0 · 兑现

| ID | 项 | 验收 |
| --- | --- | --- |
| C-1 | `verdictFate(...)` 纯查询 | 只看文件是否存在与过期时间，三态；不做任何推断 |
| C-2 | 行上说出下场 | 本机：已写出 / **已被取走** / 过期未取走；远端：维持今天那句话 |
| C-3 | 取走之后仍留一会儿 | 请求文件被清掉后下场不能立刻消失，否则用户永远看不到那一秒的回执 |
| C-4 | 不越界 | 远端**永不**报「已被取走」；`.used` 不在盘上就不说它在 |

### P0 · 结构

| ID | 项 | 验收 |
| --- | --- | --- |
| S2-a | 叙事/格式化搬出 `StatusStore` | 行叙事、观测行、信号行、可读化、时长与 token 格式化整组进 `StatusStoreNarration.swift` |
| S2-b | Support Health 格式化搬出 | **评估后不做** —— 那一组里 `supportObservedDetail` 用 `cachedAll`、`supportFailureTimelineDetail` 用 `harvestSupervisor`，两个都是 `private`。要搬就得把 `cachedAll` 放宽成 internal，那是拿真实的封装换行数；把一组内聚的函数拆成两半放两个文件更差。留在原处，理由记在这里 |
| S2-c | 零行为变更 | 只搬不改；`StatusStore.swift` 5019 → 4068（−951，−19%）；测试不动一行仍然全绿 |

### 明确不做

| 项 | 理由 |
| --- | --- |
| 从笔录推断厂商是否采纳 | 没有证据说明那个记录存在。假设它在，就是在犯本版要修的错 |
| 远端也报「已被取走」 | `.used` 在另一台机器上，回不回来 Pulse 无从得知 |
| Fleet | 在一条连自己结果都报不出来的路径上再盖一层跨机器观测，是在没验收的地基上加楼层 |
| 自动重试判决 | 判决单次使用、90 秒过期是安全模型的一部分，不碰 |
