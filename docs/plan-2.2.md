## 新信息：CPU 不是从 `%cpu` 来的

2.1 的笔录增长速率回答「它在不在**产出**」。但产出是结果，产出之前有一段只有
CPU 才看得见的时间：跑测试、装依赖、编译、等一个长工具调用 —— 笔录一动不动，
进程忙得要死。只看文件，这段时间与「卡住了」长得一模一样。

**取值方式必须讲究。** `ps` 的 `%cpu` 在 macOS 上是**进程生命周期的平均值**，
对一个开了三小时的 Agent 几乎没有信息量 —— 拿它当「此刻在忙」是撒谎。

正确的做法与 2.1 的增长速率**同构**：读累计 CPU 时间（`cputime`），记住上一拍的
(累计值, 墙钟)，两拍相减得到**这段时间里真实的 CPU 占用**。同一个 `ps` fork 里
顺带把 `rss` 也取了，零额外成本、无新权限、不碰 TCC。

于是三种状态第一次可分：

| CPU | 笔录增长 | 含义 |
| --- | --- | --- |
| 高 | 在长 | 正在产出 |
| 高 | 不动 | **在算**（跑测试 / 编译 / 长工具调用）—— 以前这里显示得像卡住 |
| ~0 | 不动 | 真的停了 |

诚实条款照旧：**采样不足两拍就说不知道**（首次见到的进程没有前一拍可减），
compaction / pid 复用一律归零重来。

### 明确不做

| 项 | 理由 |
| --- | --- |
| 用 `%cpu` 字段 | 它是生命周期平均值，当「此刻」用就是撒谎 |
| CPU 曲线 / 历史图 | 趋势图仍在非目标里 |
| 给 CPU 单独发一种灯色 | 状态编码上限 4 种，没论证不加 |
| 每拍多 fork 一次 ps | 新字段必须搭现有那一次调用；省电是硬约束 |
